# Keyboard navigation accessibility checklist

Use this manual-first checklist for keyboard and pointer access in web interfaces. WCAG 2.2 Level AA includes both Level A and Level AA criteria. Expected results below describe those requirements unless marked **Recommended**; testing methods and tool choices are recommendations, not mandated implementations.

This is guidance, not an audit report, an exhaustive conformance assessment, or certification. Passing these checks or an automated scan does not establish conformance. Consult the [WCAG 2.2 standard](https://www.w3.org/TR/WCAG22/) and [quick reference](https://www.w3.org/WAI/WCAG22/quickref/) for complete requirements and exceptions.

## Prepare and record

Choose representative pages and complete journeys, such as sign-in, search, editing, and submission. Include desktop/mobile layouts, zoom, and dialog, menu, tooltip, loading, error, and success states. Use safe test accounts and data. Start with the screen reader off so its navigation does not mask keyboard failures; repeat relevant interactions with it on.

Record **Pass**, **Fail**, or **Not applicable** with a reason per check, page, and state. Leave untested checks unassessed and list them as coverage gaps. Include URL/build, role, OS/browser/assistive-technology versions, input method, viewport, zoom, theme, reproduction steps, expected/actual behavior, and evidence without secrets. Retest fixes and the complete affected journey. The [audit overview](./manual-accessibility-checklist.md#record-results) has a reusable recording template and links to the other four categories.

## Tools

| Tool | Use |
| --- | --- |
| Keyboard alone | Test Tab, Shift+Tab, Enter, Space, arrow keys, and Escape as appropriate. On macOS, enable system/browser keyboard navigation so all controls are reachable. |
| Browser DevTools and accessibility tree | Inspect active focus, DOM order, computed roles/states, CSS target dimensions, and scroll containers; use zoom and responsive viewports for obscured focus checks. |
| Screen readers | Repeat key journeys with NVDA and Firefox/Chrome on Windows, VoiceOver and Safari on macOS/iOS, or TalkBack and Chrome on Android, according to supported environments. |
| axe DevTools, Accessibility Insights, or WAVE | Complement manual checks with scans in each exposed state. Inspect reported keyboard/focus issues manually; scanners cannot prove a journey is operable. |
| Optional axe-core with Playwright/Cypress | Add automated regression scans and scripted keyboard/focus assertions for repaired journeys; retain manual review. |

## Checks

| Check | Manual steps | Expected pass result and criteria |
| --- | --- | --- |
| Complete journeys | Set the pointer aside. Complete each journey using only the keyboard, including menus, pickers, uploads, error recovery, and final submission. Try the documented keys for custom widgets. | All functionality is keyboard-operable without requiring specific keystroke timing, except functions whose underlying input depends on the path of movement rather than endpoints. **2.1.1 Keyboard (A)**. |
| Focus order and traps | Tab forward and backward through each layout and widget. Enter and leave embedded content. Open a modal, navigate it, dismiss it, and continue the journey. | Focus order preserves meaning and operability. Keyboard focus can leave components; any nonstandard exit method is explained. An active modal keeps background content inactive. **Recommended modal pattern:** move focus inside, contain Tab within it, support Escape where appropriate, and restore focus to the opener or a logical successor. These patterns support **2.4.3 Focus Order (A), 2.1.2 No Keyboard Trap (A), 4.1.2 Name, Role, Value (A)**; modal containment is not itself an inescapable trap. |
| Visible, unobscured focus | Follow every focus stop, including inside scroll containers and under sticky headers, cookie banners, and bottom bars. Repeat at zoomed and mobile layouts. | A keyboard focus indicator is visible, and the focused component is not entirely hidden by author-created content. **2.4.7 Focus Visible (AA), 2.4.11 Focus Not Obscured (Minimum) (AA)**. User-opened content may obscure focus if it can be revealed without advancing focus; user-movable content is evaluated in its initial position. **Recommended:** keep the entire control and indicator visible; that is stronger than the AA obscuration minimum. |
| Skip repeated navigation | Reload and use the first keyboard stops. Activate the skip link or another bypass mechanism and continue navigating. | A working mechanism bypasses repeated blocks; a skip link, when used, becomes visible on focus and moves navigation to the intended content. **2.4.1 Bypass Blocks (A)**. A skip link is a recommended technique, not the only permitted mechanism. |
| Hover and focus content | Reveal tooltips, popovers, and submenus by hover and keyboard focus. Move the pointer onto the new content, dismiss it, and test without moving pointer or focus. | Additional content is dismissible without moving hover/focus unless it communicates an input error or does not obscure/replace content; it is hoverable and persists until dismissed, no longer valid, or hover/focus is removed. Author-controlled content meets these rules; browser-controlled content is excepted. **1.4.13 Content on Hover or Focus (AA)**. |
| Pointer and dragging alternatives | For maps, sliders, sortable items, and drag-and-drop, try a single-pointer method without dragging, then test keyboard access independently. Test any multipoint or path-based gestures too. | Dragging has a single-pointer non-drag alternative unless essential or determined by an unmodified user agent. Multipoint/path-based gestures have a single-pointer alternative without a path-based gesture unless essential. Keyboard support alone does not satisfy the pointer alternative. **2.5.7 Dragging Movements (AA), 2.5.1 Pointer Gestures (A)**. |
| Target size | Measure small pointer targets in CSS pixels with DevTools, including icon buttons and adjacent controls on mobile. | Targets are at least **24 by 24 CSS pixels**, or an exception applies: sufficient spacing, an equivalent compliant control on the same page, inline targets in sentences or constrained by surrounding non-target line height, unmodified user-agent controls, or an essential/legally required presentation. For undersized targets using spacing, center a 24 CSS pixel diameter circle on each target's bounding box: it must not intersect another target or another undersized target's circle. Document the exception used. **2.5.8 Target Size (Minimum) (AA)**. |
| Shortcuts and pointer cancellation | Try single-character shortcuts while typing and using speech input. Press a pointer control, move away, and release. | Character-key shortcuts can be disabled, remapped to include a non-character key, or are active only when the relevant component has focus. Pointer actions avoid down-event activation, allow abort/undo, or reverse on release, unless down-event completion is essential. **2.1.4 Character Key Shortcuts (A), 2.5.2 Pointer Cancellation (A)**. |

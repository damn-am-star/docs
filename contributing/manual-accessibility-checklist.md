# Manual accessibility audit checklist

Use this manual-first checklist to evaluate web interfaces against **WCAG 2.2 Level AA**, which includes both Level A and Level AA success criteria. Each row gives an action and an expected result. Record a separate result for each applicable page, component, state, and environment.

This is a practical starting point, not an exhaustive checklist or certification of conformance. Conformance also requires evaluating every applicable criterion and the WCAG conformance requirements, including full pages and complete processes. Automated scans cannot establish conformance, and passing this checklist does not prove that an interface is accessible to everyone. This document is testing guidance, not a report of tests performed.

The authoritative sources are the [WCAG 2.2 standard](https://www.w3.org/TR/WCAG22/) and the [customizable WCAG 2.2 quick reference](https://www.w3.org/WAI/WCAG22/quickref/). Criterion numbers below refer to that standard. Unless marked **Recommended**, expected results describe A or AA requirements; suggested testing techniques and tool combinations are recommendations, not mandated implementations.

## Set up the audit

1. Define the scope: URLs, build or commit, roles, permissions, languages, third-party integrations, and excluded areas. Include representative templates and all pages in selected complete processes, not just the home page.
1. Choose full journeys such as sign-in and account recovery, search and filtering, form submission, purchase, and editing or deleting information. Use safe test accounts and data.
1. Include desktop and mobile responsive layouts, portrait and landscape, relevant themes, and dialogs, menus, tooltips, expanded panels, loading, empty, error, and success states. Test responsive functionality, not only screenshots.
1. Record operating system, browser and version, assistive technology and version, device or input method, viewport in CSS pixels, zoom or text-size settings, and theme. Start keyboard-only testing with the screen reader off; then repeat relevant journeys with it on.
1. Run complementary automated checks on each significant state, then perform the manual checks below. Deduplicate findings, repair root causes, and retest the original steps and affected journeys.

**Recommended:** Include people with disabilities in usability testing. Select browser and assistive-technology combinations based on the supported audience, and document coverage gaps. One combination cannot demonstrate universal accessibility.

### Record results

Use **Pass**, **Fail**, or **Not applicable** for each check. Explain every Not applicable result, such as "no live synchronized media in scope." Do not mark an untested check Pass or Not applicable: leave it unassessed and list it as a coverage gap.

Copy this record for each finding or checked scenario:

| Field | What to record |
| --- | --- |
| Check and criterion | Checklist row, WCAG success criterion number and level |
| Scope and state | URL, build, role, journey step, component, and state |
| Environment | OS, browser, assistive technology and versions; input, viewport, zoom, theme |
| Result | Pass / Fail / Not applicable, with justification |
| Reproduction | Numbered steps, starting conditions, and test data without secrets |
| Expected / actual | Observable expected behavior and what happened instead |
| Evidence | Screenshot, recording, accessibility-tree details, measurements, or announcement transcript; remove sensitive data |
| Follow-up | User impact, owner, issue link, fix, and retest result and environment |

## Tools

| Tool | Practical use |
| --- | --- |
| Keyboard alone | Use Tab, Shift+Tab, Enter, Space, arrow keys, and Escape as appropriate. Check complete journeys, focus, and widget interactions without a mouse. On macOS, enable keyboard navigation in system/browser settings so controls are reachable. |
| NVDA with Firefox or Chrome on Windows | Check browse mode for document structure and forms/focus mode for controls. Test announcements as well as operation. |
| VoiceOver with Safari on macOS and iOS | On macOS, use VoiceOver navigation and the rotor. On iOS, use swipe navigation, the rotor, and touch exploration on an actual device. |
| TalkBack with Chrome on Android | Use swipe navigation, reading controls, and touch exploration on an actual device. |
| Browser DevTools and accessibility tree | Inspect computed names, roles, states, relationships, language, focus, DOM order, CSS pixel dimensions, and computed styles. Inspection complements, but does not replace, assistive-technology use. |
| [TPGi Colour Contrast Analyser](https://www.tpgi.com/color-contrast-checker/) | Measure foreground/background contrast, including hover, focus, error, and selected states. Sample the least favorable area of gradients and images. |
| Browser zoom and text-spacing tools | Use browser zoom, text-only resize where available, responsive viewport controls, and a text-spacing bookmarklet or DevTools style overrides. Confirm actual CSS viewport width and computed styles. |
| [axe DevTools](https://www.deque.com/axe/devtools/), [Accessibility Insights](https://accessibilityinsights.io/), or [WAVE](https://wave.webaim.org/) | Find machine-detectable issues and guide inspection. Open dialogs and expose validation, loading, and success states before scanning them. Manually resolve items needing judgment. |
| Optional: axe-core with Playwright or Cypress | Add automated regression checks for representative routes and interactive states. These do not replace keyboard, screen-reader, visual, or media checks. |

## Keyboard navigation

| Check | Manual steps | Expected pass result and criteria |
| --- | --- | --- |
| Complete journeys | Set the pointer aside. Complete each journey using only the keyboard, including menus, pickers, uploads, error recovery, and final submission. Try the documented keys for custom widgets. | All functionality is keyboard-operable without requiring specific keystroke timing, except functions whose underlying input depends on the path of movement rather than endpoints. **2.1.1 Keyboard (A)**. |
| Focus order and traps | Tab forward and backward through each layout and widget. Enter and leave embedded content. Open a modal, navigate it, dismiss it, and continue the journey. | Focus order preserves meaning and operability. Keyboard focus can leave components; any nonstandard exit method is explained. An active modal keeps background content inactive. **Recommended modal pattern:** move focus inside, contain Tab within it, support Escape where appropriate, and restore focus to the opener or a logical successor. These patterns support **2.4.3 Focus Order (A), 2.1.2 No Keyboard Trap (A), 4.1.2 Name, Role, Value (A)**; modal containment is not itself an inescapable trap. |
| Visible, unobscured focus | Follow every focus stop, including inside scroll containers and under sticky headers, cookie banners, and bottom bars. Repeat at zoomed and mobile layouts. | A keyboard focus indicator is visible, and the focused component is not entirely hidden by author-created content. **2.4.7 Focus Visible (AA), 2.4.11 Focus Not Obscured (Minimum) (AA)**. User-opened content may obscure focus if it can be revealed without advancing focus; user-movable content is evaluated in its initial position. **Recommended:** keep the entire control and indicator visible; that is stronger than the AA obscuration minimum. |
| Skip repeated navigation | Reload and use the first keyboard stops. Activate the skip link or another bypass mechanism and continue navigating. | A working mechanism bypasses repeated blocks; a skip link, when used, becomes visible on focus and moves navigation to the intended content. **2.4.1 Bypass Blocks (A)**. A skip link is a recommended technique, not the only permitted mechanism. |
| Hover and focus content | Reveal tooltips, popovers, and submenus by hover and keyboard focus. Move the pointer onto the new content, dismiss it, and test without moving pointer or focus. | Additional content is dismissible without moving hover/focus unless it communicates an input error or does not obscure/replace content; it is hoverable and persists until dismissed, no longer valid, or hover/focus is removed. Author-controlled content meets these rules; browser-controlled content is excepted. **1.4.13 Content on Hover or Focus (AA)**. |
| Pointer and dragging alternatives | For maps, sliders, sortable items, and drag-and-drop, try a single-pointer method without dragging, then test keyboard access independently. Test any multipoint or path-based gestures too. | Dragging has a single-pointer non-drag alternative unless essential or determined by an unmodified user agent. Multipoint/path-based gestures have a single-pointer alternative without a path-based gesture unless essential. Keyboard support alone does not satisfy the pointer alternative. **2.5.7 Dragging Movements (AA), 2.5.1 Pointer Gestures (A)**. |
| Target size | Measure small pointer targets in CSS pixels with DevTools, including icon buttons and adjacent controls on mobile. | Targets are at least **24 by 24 CSS pixels**, or an exception applies: sufficient spacing, an equivalent compliant control on the same page, inline targets in sentences or constrained by surrounding non-target line height, unmodified user-agent controls, or an essential/legally required presentation. For undersized targets using spacing, center a 24 CSS pixel diameter circle on each target's bounding box: it must not intersect another target or another undersized target's circle. Document the exception used. **2.5.8 Target Size (Minimum) (AA)**. |
| Shortcuts and pointer cancellation | Try single-character shortcuts while typing and using speech input. Press a pointer control, move away, and release. | Character-key shortcuts can be disabled, remapped to include a non-character key, or are active only when the relevant component has focus. Pointer actions avoid down-event activation, allow abort/undo, or reverse on release, unless down-event completion is essential. **2.1.4 Character Key Shortcuts (A), 2.5.2 Pointer Cancellation (A)**. |

## Screen readers

| Check | Manual steps | Expected pass result and criteria |
| --- | --- | --- |
| Semantics and reading order | Read each page linearly, then navigate headings, landmarks, lists, and tables. Compare the spoken sequence with the visual meaning and accessibility tree. Repeat in responsive layouts. | Structure and relationships are programmatically determinable; the reading sequence preserves meaning. Table headers associate with the correct cells. **1.3.1 Info and Relationships (A), 1.3.2 Meaningful Sequence (A)**. **Recommended:** use native HTML, a clear heading hierarchy, and useful landmarks. |
| Names, roles, and states | Navigate every control, including icon-only buttons and custom widgets. Activate it and change its state. Inspect its computed accessible name and role. | Name and role are programmatically determinable; user-set states, properties, and values are exposed, and changes are available to assistive technology. Expanded, selected, checked, and disabled states match behavior. **4.1.2 Name, Role, Value (A)**. |
| Visible label matches name | Compare each visible text label with the computed accessible name. Optionally activate controls with speech input using their visible label. | The accessible name contains the visible text label, including text presented as an image. **2.5.3 Label in Name (A)**. **Recommended:** start the name with the visible label. |
| Image alternatives | Read meaningful images, linked images, charts, and decorative images with the screen reader; compare alternatives with the image's purpose in context. | Text alternatives convey equivalent information or function. Decorative images are ignored, not announced as filenames. Complex charts have equivalent information; specialized cases such as tests, sensory experiences, and CAPTCHAs follow the criterion's specific provisions. **1.1.1 Non-text Content (A)**. |
| Links, headings, and page titles | List links and headings, read ambiguous links in their programmatically determined context, and switch between pages or tabs. | Link purpose is understandable from its text alone or its programmatic context, except where ambiguous to users generally. Headings and labels describe topic or purpose; page titles identify topic or purpose. **2.4.4 Link Purpose (In Context) (A), 2.4.6 Headings and Labels (AA), 2.4.2 Page Titled (A)**. **Recommended:** prefer useful standalone link text. |
| Dynamic status messages | Trigger a search result count, loading/progress message, saved confirmation, and validation error without deliberately moving focus. Listen once and inspect updates. | Status messages are programmatically determinable through role or properties so they can be presented without receiving focus. Updates are announced at an appropriate urgency. **4.1.3 Status Messages (AA)**. **Recommended:** avoid duplicate announcements, announcing every keystroke, or moving focus merely to read a routine update. |
| Language | Check the document's language and passages in other languages in the accessibility tree or markup; listen with suitable voices installed. | The page language and changes in passage language are programmatically determinable, except proper names, technical terms, indeterminate language, and words adopted into the surrounding language. **3.1.1 Language of Page (A), 3.1.2 Language of Parts (AA)**. |

## Color contrast and visual presentation

| Check | Manual steps | Expected pass result and criteria |
| --- | --- | --- |
| Text contrast | Measure text against its actual background in every theme and interaction state, including placeholders and text over images. | At least **4.5:1** for normal text, or **3:1** for large text: at least **18 pt (24 CSS px)** regular or **14 pt (about 18.67 CSS px)** bold. Logos, incidental text, and text in inactive controls are excepted. Do not round a failing ratio up. **1.4.3 Contrast (Minimum) (AA)**. |
| Non-text contrast | Measure visual information needed to identify controls/states and understand meaningful graphics against adjacent colors. Include focus and selected states where applicable. | Required visual information has at least **3:1** contrast. Inactive controls and unmodified user-agent control appearances are excepted; graphics have an exception where a particular presentation is essential. Not every border or decorative graphic requires 3:1. **1.4.11 Non-text Contrast (AA)**. |
| Non-color cues | Inspect errors, links, charts, and selected states in grayscale or with color removed. Check instructions that mention color, shape, position, or sound. | Color is not the sole means of conveying information, actions, or distinctions; instructions do not depend solely on sensory characteristics. Use text, patterns, shapes, or other cues. **1.4.1 Use of Color (A), 1.3.3 Sensory Characteristics (A)**. |
| Text resize | Increase text size to **200%** using browser zoom or text-only resizing, without assistive technology. Complete the journey and inspect controls and messages. | Text resizes without loss of content or functionality; captions and images of text are excepted. **1.4.4 Resize Text (AA)**. Also check that real text is used rather than images of text unless customizable or essential. **1.4.5 Images of Text (AA)**. |
| Reflow and orientation | Test a viewport **320 CSS pixels wide**, or 400% zoom from an initial 1280 CSS pixel width, verifying the resulting viewport. Test portrait and landscape. | Vertically scrolling content needs no two-dimensional scrolling and loses no information or functionality. For horizontally scrolling content, test a height of **256 CSS pixels**. Parts requiring a two-dimensional layout for meaning or use, such as data tables or maps, are excepted, not the entire page. Orientation is not restricted unless essential. **1.4.10 Reflow (AA), 1.3.4 Orientation (AA)**. |
| Text spacing | Apply all overrides together: line height **1.5 times** font size, paragraph spacing **2 times**, letter spacing **0.12 times**, word spacing **0.16 times**. Inspect navigation, inputs, dialogs, and long text. | No loss of content or functionality from these overrides where the markup supports them. Languages/scripts that do not use a spacing property need only support applicable properties. These are override tolerances, not required default design settings. **1.4.12 Text Spacing (AA)**. |

## Forms and authentication

| Check | Manual steps | Expected pass result and criteria |
| --- | --- | --- |
| Labels, instructions, and groups | Navigate inputs with keyboard and screen reader. Check required status, formats, examples, checkbox/radio groups, and label activation. | Inputs have descriptive labels or instructions and programmatic relationships; related groups have a meaningful group label. A placeholder alone is not a sufficient persistent label. **1.3.1 Info and Relationships (A), 3.3.2 Labels or Instructions (A), 4.1.2 Name, Role, Value (A)**. |
| Input purpose and autocomplete | Inspect fields collecting information about the user, such as name, email, address, and password, and try browser autofill. | For fields serving a purpose in WCAG's defined input-purpose list, that purpose is programmatically determinable where supported by the technology, commonly with valid HTML `autocomplete` tokens. **1.3.5 Identify Input Purpose (AA)**. **Recommended:** use suitable input types and mobile keyboards too. |
| Errors and recovery | Submit empty and invalid values, then correct them using keyboard and screen reader. Check both field-level and server-side errors. | Detected errors identify the affected item and describe the error in text. Known correction suggestions are supplied unless they jeopardize security or purpose. Errors and their relationships are accessible. **3.3.1 Error Identification (A), 3.3.3 Error Suggestion (AA), 1.3.1 (A)**. **Recommended:** preserve valid entries and provide a linked error summary for long forms. |
| Predictability | Focus controls and change selections without submitting. Compare repeated navigation and same-function controls across pages. | Focus alone does not initiate a context change; changing a setting does not unexpectedly change context unless the user was advised beforehand. Repeated navigation has consistent relative order and same-function components have consistent identification. **3.2.1 On Focus (A), 3.2.2 On Input (A), 3.2.3 Consistent Navigation (AA), 3.2.4 Consistent Identification (AA)**. |
| Important submissions | Safely exercise legal/financial transactions, changes/deletions of user-controllable stored data, and test-response submissions. Try review, correction, cancellation, and reversal. | At least one safeguard exists: submission is reversible, data is checked for input errors with an opportunity to correct, or users can review, confirm, and correct before finalizing. **3.3.4 Error Prevention (Legal, Financial, Data) (AA)**. |
| Redundant entry | Complete a multistep process and look for information requested again, including details entered earlier or provided to the user. | Previously supplied information in the same process is auto-populated or selectable unless re-entry is essential, required for security, or the information is no longer valid. **3.3.7 Redundant Entry (A)**. |
| Accessible authentication | Test every authentication step, including recovery and multifactor challenges. Try a password manager, autofill, copying/pasting passwords and codes, and any alternative method. | No cognitive function test, such as remembering a password, solving a puzzle, or transcribing a code, is required unless there is a non-cognitive alternative, a mechanism assisting completion, an object-recognition test, or recognition of personal non-text content the user supplied to the site. Password-manager and paste support are practical assistance mechanisms; do not block them. Object recognition/personal content are AA exceptions, not blanket CAPTCHA exemptions; alternatives must still satisfy other criteria such as 1.1.1. **3.3.8 Accessible Authentication (Minimum) (AA)**. |
| Time limits | Trigger session expiration and timed steps using test settings where possible. Try disabling, adjusting, or extending the limit and read warnings with assistive technology. | For each content-set time limit, users can turn it off beforehand, adjust it beforehand over at least ten times the default, or extend it after a warning giving at least 20 seconds for a simple action, at least ten times. Exceptions: real-time events with no alternative, essential limits, or limits longer than 20 hours. **2.2.1 Timing Adjustable (A)**. **Recommended:** preserve work across reauthentication. |
| Consistent help | Compare pages containing repeated contact details, contact mechanisms, self-help, or automated contact. Navigate them with a screen reader. | Repeated help mechanisms occur in the same relative order to other content, unless the user initiates the change. The criterion does not require adding help where none exists. **3.2.6 Consistent Help (A)**. |

## Media

| Check | Manual steps | Expected pass result and criteria |
| --- | --- | --- |
| Prerecorded captions | Play prerecorded video with audio and turn captions on. Compare the whole recording with speech, speakers, and meaningful sounds. | Synchronized captions provide equivalent speech and relevant non-speech audio, including speaker identification where needed. Media that is a clearly labeled alternative for text has an exception. **1.2.2 Captions (Prerecorded) (A)**. Automatic captions need human review and correction. |
| Live captions | Observe a representative live synchronized stream with captions enabled, including speaker changes and important sounds. | Captions convey the live audio information in synchronized media. **1.2.4 Captions (Live) (AA)**. **Recommended:** assess caption accuracy and latency with actual users. |
| Audio description | Listen to prerecorded synchronized video without viewing it. Identify meaningful visual action, on-screen text, and scene changes absent from the main audio; enable the described version. | Audio description conveys needed visual information. If all meaningful visuals are already conveyed by the soundtrack, additional description is unnecessary. A transcript alone does **not** satisfy **1.2.5 Audio Description (Prerecorded) (AA)**. The Level A alternative in **1.2.3 (A)** permits audio description or a time-based media alternative, with a labeled text-alternative exception; that does not remove the AA description requirement. |
| Standalone audio/video alternatives | Inspect prerecorded audio-only and silent video-only content, including its alternative. | Audio-only has an equivalent time-based media alternative, typically a transcript; video-only has an equivalent time-based media alternative or audio track. Clearly labeled media alternatives for existing text are excepted. **1.2.1 Audio-only and Video-only (Prerecorded) (A)**. **Recommended:** provide a descriptive transcript alongside synchronized media too. |
| Player operation | Use only the keyboard, then a screen reader, to play/pause, seek, change volume, toggle captions/description, and enter/exit fullscreen where provided. | Available controls are keyboard-operable, named, expose states, have visible focus, and create no keyboard trap. **2.1.1 (A), 2.1.2 (A), 2.4.7 (AA), 4.1.2 (A)**. Native players still need evaluation in supported environments. |
| Autoplay audio and movement | Load pages and trigger moving, blinking, scrolling, and auto-updating content. Locate pause/stop/hide and volume controls without using a pointer. | Automatically playing audio lasting more than **3 seconds** can be paused/stopped or its volume controlled independently of system volume. Moving/blinking/scrolling content that starts automatically, lasts more than **5 seconds**, and appears alongside other content can be paused/stopped/hidden unless essential. Automatically updating content alongside other content can be paused/stopped/hidden or its update frequency controlled unless essential; it has no five-second exemption. **1.4.2 Audio Control (A), 2.2.2 Pause, Stop, Hide (A)**. **Recommended:** avoid autoplay audio and honor reduced-motion preferences; reduced-motion support alone does not satisfy these criteria. |
| Flashing | Identify flashing video, animations, and transitions. Do not repeatedly watch suspect material; use qualified analysis of the rendered content when needed. | Nothing flashes more than **three times in any one-second period**, or flashes remain below the general-flash and red-flash thresholds. Thresholds depend on luminance/color changes and combined flashing area, not just frequency: use the standard's definitions and qualified analysis rather than a visual guess. **2.3.1 Three Flashes or Below Threshold (A)**. **Recommended:** avoid flashing entirely. |

## Close out the audit

Record scope and coverage gaps alongside the findings, including unsupported combinations, untested states, and unavailable live events. Prioritize by user impact and whether someone can complete the journey, not only by scanner severity. Retest fixes in the original environment and check related components and full processes for regressions.

Report only what the evidence supports: for example, "these checks passed for this build, scope, and environment," not "WCAG certified." Revisit the full standard for requirements not covered here before making any conformance claim.
